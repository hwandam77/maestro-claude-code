## 5. 성능 벤치마크

### 5.1 Streaming Throughput 및 TTFT (Time To First Token)

**단일 요청 성능** (prompt: ~50 tokens, generation: 500 tokens)

| 메트릭 | 값 |
|--------|-----|
| **TTFT (첫 토큰까지 시간)** | 0.144s |
| **생성 토큰** | 500 |
| **생성 시간** | 8.061s |
| **Throughput** | 62.0 tok/s |

**분석**: TTFT가 0.14초로 매우 낮으며, 생성 처리량이 안정적으로 62 tok/s를 유지.

### 5.2 Context Length별 TTFT

컨텍스트 길이에 따른 첫 토큰 생성 시간 측정:

| 프롬프트 길이 | TTFT | 증가율 |
|-------------|------|--------|
| ~50 tokens | 0.091s | baseline |
| ~500 tokens | 0.372s | +309% |
| ~2,000 tokens | 1.114s | +1124% |
| ~4,000 tokens | 1.506s | +1556% |

**분석**:
- 짧은 프롬프트에서는 TTFT가 0.09초로 매우 우수함
- 4K 토큰 컨텍스트에서도 1.5초 이내로 제어됨 (비교: 72B 모델 3.25초)
- 긴 컨텍스트 처리 시 여전히 빠른 응답 시간 유지

### 5.3 Batch Scaling (동시 다중 요청)

8개까지 확장 가능한 동시 요청 처리 성능:

| 동시 요청 | Wall Time | 평균 TTFT | 요청당 TPS | 시스템 TPS | 총 토큰 |
|----------|-----------|-----------|-----------|-----------|---------|
| 1 | 1.67s | 0.065s | 62.5 | 59.9 | 100 |
| 2 | 1.74s | 0.065s | 60.5 | 115.2 | 200 |
| 4 | 1.86s | 0.109s | 57.5 | 215.3 | 400 |
| 8 | 2.08s | 0.162s | 52.5 | 384.1 | 800 |
| 16 | 2.75s | 0.316s | 41.3 | 580.8 | 1600 |

**분석**:

- **선형 확장성**: 동시 요청 8개까지는 시스템 TPS가 선형에 가깝게 증가 (384.1 tok/s)
- **최대 처리량**: 16개 동시 요청 시 580.8 tok/s로 피크 달성 (개별 요청 TPS는 감소하나 총 처리량 최대화)
- **큐 대기**: 16개 요청 시 평균 TTFT가 0.316s로 증가 (큐 대기 시간 누적)
- **메모리 안정성**: 전체 테스트 중 OOM 미발생

## 7. Tool Calling 호환성 분석

### 현황 분석

서버 설정에 `--enable-auto-tool-choice`와 `--tool-call-parser hermes`를 추가했으나, 주목할 점:

**문제점**:
- Qwen2.5-Coder-32B 모델은 OpenAI 표준 `tool_calls` 배열이 아닌, response `content` 내 `<tools>` 태그로 응답
- Hermes 포맷 완벽 지원하지 않을 수 있음

**현재 동작**:
- Tool Calling 기능 자체는 동작함
- 클라이언트에서 응답 파싱 시 content 내 XML/태그 형식으로 파싱 필요
- 표준 OpenAI 호환 클라이언트는 `tool_calls` 배열 기대로 호환성 문제 가능

**권고**:
- 클라이언트 라이브러리가 Qwen 형식의 tool calling을 지원하는지 확인 필요
- 필요 시 응답 후처리 로직 추가

## 8. 참고사항 및 권고

### 주요 설정 변경의 영향

#### 1. max-model-len: 8192 → 32768
- **영향**: 최대 4배 긴 코드 컨텍스트 처리 가능
- **활용**: 수천 줄의 소스 코드 분석 가능
- **트레이드오프**: 메모리 사용량은 동일 (모델 로드 후 고정)

#### 2. max-num-seqs: 64 → 128
- **영향**: 동시 요청 처리 능력 증대
- **활용**: 더 많은 사용자 동시 접속 지원
- **안정성**: 벤치마크 상 메모리 압박 없음

#### 3. gpu-memory-utilization: 0.92
- **영향**: GPU 메모리 92% 할당 (여유 8%)
- **안정성**: 안정적 운영 범위 (90-95% 권장)
- **모니터링**: 온도 및 메모리 압박 주시

#### 4. CUDA Graph PIECEWISE 모드
- **영향**: 추론 커널 최적화로 처리량 개선
- **오버헤드**: CPU 컴파일 시간 약간 증가
- **효과**: 배치 요청에서 더 큰 이점

### 모니터링 권고사항

#### GPU 온도
- **정상 범위**: 40-70°C
- **경고 임계값**: > 80°C
- **점검 주기**: 일 1회 (peak hours)

#### GPU 메모리
- **목표**: 90-95% 활용
- **경고 임계값**: > 96% (OOM 위험)
- **모니터링 명령어**: `nvidia-smi`

#### API 응답 성능
- **목표 TTFT**: 0.1-0.2s (일반 요청)
- **목표 처리량**: 50+ tok/s
- **모니터링 명령어**: vLLM 대시보드 또는 로그 분석

### 트러블슈팅 가이드

#### 증상: 느린 응답 (TTFT > 1s)
1. 동시 요청 수 확인: `curl http://192.168.0.14:8000/stats`
2. 큐에 대기 중인 요청이 많으면 정상 (배치 처리)
3. 지속적으로 느리면 GPU 온도 확인

#### 증상: Tool Calling 응답 파싱 실패
1. 응답 형식이 Qwen 표준인지 확인 (XML 태그 형식)
2. 클라이언트 파서가 content 내 태그를 지원하는지 검증
3. 필요 시 후처리 로직 추가

#### 증상: GPU 메모리 부족
1. 실행 중인 프로세스 확인: `ps aux | grep vllm`
2. 필요 시 vLLM 재시작: `systemctl restart vllm` 또는 수동 재시작
3. Xorg 프로세스 확인 및 필요 시 종료
